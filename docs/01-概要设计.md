# WatchDesk 概要设计

## 1. 项目概述

WatchDesk 是一个**工作流编排容器**，以桌面客户端形态运行于 Windows / macOS。

核心定位：

- **容器** — 承载各类工具型 Web Component（计数器、文件浏览器、终端、工作流编辑器等）
- **文件浏览器** — 对本地文件系统的高性能浏览与管理
- **工作流编排** — 工具间可组合、可编排，形成自动化工作流

## 2. 架构风格

### 2.1 DDD 四层架构

```
┌──────────────────────────────────────────────────────┐
│  Presentation  │  solid-element Web Components       │
│                │  每个工具 = 一个 Custom Element      │
├────────────────┼──────────────────────────────────────┤
│  Application   │  Use Cases                           │
│                │  编排 Domain 对象，处理命令/查询     │
├────────────────┼──────────────────────────────────────┤
│  Domain        │  Entity / Value Object / Repository  │
│                │  纯 TypeScript，零 I/O 依赖          │
├────────────────┼──────────────────────────────────────┤
│  Infrastructure│  Native Bridge (Phase 1: stub)       │
│                │  Electron IPC / File System / OS     │
└────────────────┴──────────────────────────────────────┘
```

### 2.2 边界 / 内部分离

架构的**根本原则**：所有不安全、需防御、需回退的逻辑集中在边界层。边界之内，TypeScript 类型系统保证零防御代码。

```
┌─────────── 边界层 (Boundary) ───────────┐
│  所有可选链、兜底、try/catch 集中于此     │
│                                          │
│  IPC Handler · Native Adapter            │
│  DOM Event · contextBridge               │
│  ElectronRepo · zod schema               │
└──────────────┬───────────────────────────┘
               │  Result<T, E> | Branded T
               ▼
┌─────────── 内部层 (Internal) ───────────┐
│  Domain · Application · UseCase          │
│                                          │
│  零可选链 · 零兜底 · 零 try/catch         │
│  TS 编译器保证正确性                      │
└──────────────────────────────────────────┘
```

|                  | 边界层                 | 内部层                        |
| ---------------- | ---------------------- | ----------------------------- |
| `?.` `??`        | 集中出现               | **禁止**                      |
| `try/catch`      | 集中出现               | **禁止** (用 Result)          |
| `if (x == null)` | 集中出现               | **禁止** — 类型已保证         |
| `zod` / schema   | 集中出现               | 不需要                        |
| 运行时类型检查   | 集中出现               | **禁止** — 编译时已保证       |
| 类型             | `unknown` → 解析 → `T` | 精确类型 (零 `any`/`unknown`) |

### 2.3 双环境验证标准

架构是否 DDD 的判定标准：

```
同一份 renderer 源码，零改动，只替换 DI 注入的 Repo 实现：

  Electron:  ElectronCounterRepo  → 调 window.electronAPI
  Browser:   BrowserCounterRepo   → 调 localStorage

组件与 UseCase 完全不感知差异。这就是 Port/Adapter 成立。
```

| 文件                             | Electron      | Browser      | 改动           |
| -------------------------------- | ------------- | ------------ | -------------- |
| `components/watch-counter.tsx`   | ✅            | ✅           | **零**         |
| `application/counter.usecase.ts` | ✅            | ✅           | **零**         |
| `domain/repositories.ts`         | ✅            | ✅           | **零**         |
| `infrastructure/counter.repo.ts` | ElectronRepo  | BrowserRepo  | **注入时选择** |
| `infrastructure/di.ts`           | 注入 Electron | 注入 Browser | **唯一变化点** |

对应的 Main 进程同样成立：`NativeAdapter` (Rust napi-rs) → `MockAdapter` (Node fs)，UseCase 不感知。

### 2.4 层间依赖规则

```
Presentation ──→ Application ──→ Domain ←── Infrastructure
     │                │                              │
     └────────────────┴──────────────┬───────────────┘
                                     ↓
                              Domain 是核心，
                              上层依赖 Domain，
                              Infrastructure 实现 Domain 定义的接口 (DIP)
```

- **Domain 不依赖任何外层** — 纯 TS 类型和接口
- **Application 依赖 Domain** — 调用 Repository 接口，不感知实现
- **Infrastructure 实现 Domain 接口** — napi-rs / Node API / Electron IPC / localStorage
- **Presentation 依赖 Application** — Web Component 只 import UseCase，不 import 任何桥

### 2.5 跨进程 Import 约束

```
components/      ——→ import  application/       ✅
components/      ——→ import  electronAPI        ❌ 禁止
application/     ——→ import  domain/            ✅
application/     ——→ import  electronAPI        ❌ 禁止
domain/          ——→ import  electron/solid/*   ❌ 禁止
infrastructure/  ——→ import  electronAPI        ✅ 仅此层
infrastructure/  ——→ import  domain/            ✅
```

### 2.6 Monorepo 包划分

```
WatchDesk/
├── packages/
│   ├── desktop/     # Electron 桌面壳
│   └── native/      # napi-rs native module (Phase 1: stub)
└── pnpm-workspace.yaml
```

| 包                 | 职责                                     | 运行时          |
| ------------------ | ---------------------------------------- | --------------- |
| `packages/desktop` | Electron 主进程 + 渲染进程 + 预加载      | Node + Chromium |
| `packages/native`  | Rust native addon (文件 I/O, 哈希, 监听) | Node napi       |

### 2.7 依赖关系

```
@watchdesk/desktop
  ├── solid-js + solid-element   (渲染)
  ├── electron                   (运行时)
  ├── electron-vite              (构建)
  ├── electron-updater           (更新)
  └── @watchdesk/native          (native bridge)

@watchdesk/native
  ├── (Phase 2: napi-rs)
  └── (Phase 1: 仅 TS 类型声明 + stub)
```

## 4. 多进程 / 多线程 / 多协程架构

### 4.1 三层并发模型

```
┌─────────────────────────────────────────────────────────┐
│  Layer 3 — 多进程 (Process)                              │
│                                                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │  Main    │  │ Renderer │  │ Renderer │  ...          │
│  │ Process  │  │ Process 1│  │ Process 2│              │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘              │
│       │              │              │                    │
│       └──────────────┼──────────────┘                    │
│                      │ IPC (MessagePort / Uint8Array)    │
│                      │                                    │
├──────────────────────┼────────────────────────────────────┤
│  Layer 2 — 多线程 (Thread)                               │
│                                                          │
│  ┌────────────── Main Process Worker Pool ──────────┐    │
│  │                                                    │    │
│  │  HashWorker  ·  CompressWorker  ·  ScanWorker      │    │
│  │                                                    │    │
│  │  SharedArrayBuffer / Uint8Array 零拷贝              │    │
│  └────────────────────────────────────────────────────┘    │
│                                                          │
│  ┌────────────── Rust (Phase 2) ────────────────────┐    │
│  │  rayon par_iter (多文件哈希)                        │    │
│  │  tokio::spawn (协程级并发)                          │    │
│  └────────────────────────────────────────────────────┘    │
│                      │                                    │
├──────────────────────┼────────────────────────────────────┤
│  Layer 1 — 多协程 (Coroutine / Async)                    │
│                                                          │
│  Renderer: AbortController 树 · dedup · priority         │
│  Main:     Node.js Event Loop 协程调度                   │
│  Native:   tokio async runtime (Phase 2)                 │
└─────────────────────────────────────────────────────────┘
```

### 4.2 并发分配策略

| 任务类型   | 并发层               | 技术                 | Uint8Array 传输          |
| ---------- | -------------------- | -------------------- | ------------------------ |
| UI 渲染    | Process              | Chromium 独立进程    | structured clone via IPC |
| 目录枚举   | Coroutine (Main)     | async/await          | N/A                      |
| 大文件读取 | Coroutine (Rust)     | tokio::spawn         | napi zero-copy Buffer    |
| 多文件哈希 | Thread (Rust)        | rayon par_iter       | SharedArrayBuffer        |
| 文件监听   | Thread (Rust)        | notify crate + tokio | mpsc channel → IPC       |
| zstd 压缩  | Thread (Node)        | Worker thread        | postMessage              |
| 文件搜索   | Thread               | Worker thread        | N/A                      |
| 自动更新   | Coroutine (Main)     | async/await          | N/A                      |
| 协程编排   | Coroutine (Renderer) | CoroutineScheduler   | N/A                      |

### 5.4 渲染进程组件注册模型

```
Renderer Entry (main.ts)
  │
  ├── DI 组装: createDependencies()
  │     注入具体的 Repo 实现
  │
  ├── 注册 Custom Elements
  │     watch-counter
  │     watch-file-tree      (后续)
  │     watch-terminal       (后续)
  │     watch-workflow-editor(后续)
  │     watch-dashboard       (布局容器)
  │
  └── 挂载 <App> to #app
        │
        └── <watch-counter useCase={deps.counterUseCase} />
```

每个 Web Component — UseCase 通过 props 注入：

- 自身 UI (Solid JSX)
- 自身状态 (Solid createSignal/createStore)
- 通过 **注入的 UseCase** 获取数据，不直接接触 `window.electronAPI`
- 工具间通过事件总线解耦通信

## 6. 数据流

### 6.1 Renderer DDD 调用链 (以 Counter 点击为例)

```
Presentation                  Application               Infrastructure          IPC → Main
   │                             │                          │                       │
   │ <button onClick>            │                          │                       │
   │ props.useCase.increment()   │                          │                       │
   │────────────────────────────►│                          │                       │
   │                             │ repo.increment()         │                       │
   │                             │─────────────────────────►│                       │
   │                             │                          │ window.electronAPI    │
   │                             │                          │──────────────────────►│
   │                             │                          │        number         │
   │                             │                          │◄──────────────────────│
   │                             │       number             │                       │
   │                             │◄─────────────────────────│                       │
   │          number             │                          │                       │
   │◄────────────────────────────│                          │                       │
   │ setCount(n) → DOM update    │                          │                       │
   ▼                             │                          │                       │
```

**关键点**：`window.electronAPI` 仅在 `infrastructure/counter.repo.ts` 中调用，Component 和 UseCase 完全不可见。

### 6.2 完整调用链 (以读取文件为例)

```
Renderer                     Preload                     Main                      Native
  UseCase → Repo                │                          │                          │
   │ electronAPI.fs.readRaw    │                          │                          │
   │──────────────────────────►│                          │                          │
   │                            │ ipcRenderer.invoke       │                          │
   │                            │─────────────────────────►│                          │
   │                            │                          │ UseCase → Adapter       │
   │                            │                          │──────────────────────────►│
   │                            │                          │                          │ Rust: std::fs::read
   │                            │                          │       Uint8Array         │
   │                            │                          │◄─────────────────────────│
   │                            │     Uint8Array           │                          │
   │                            │◄─────────────────────────│                          │
   │     Uint8Array             │                          │                          │
   │◄───────────────────────────│                          │                          │
   │                            │                          │                          │
   ▼ 零拷贝 structured clone, 无 JSON 序列化开销                              │
```

### 6.3 Uint8Array 传输优势

| 阶段     | JSON 方式                  | Uint8Array 方式                |
| -------- | -------------------------- | ------------------------------ |
| 数据准备 | JS string → JSON.stringify | 原生 Buffer/Uint8Array         |
| IPC 传输 | 文本字符串 (UTF-16)        | 二进制 structured clone        |
| 反序列化 | JSON.parse → JS object     | 零拷贝直接使用                 |
| 内存     | 3x 拷贝                    | 1x 传递                        |
| 适用     | 小数据、配置、元数据       | 文件内容、二进制数据、哈希结果 |

**混合策略**：结构化小数据用 JSON DTO，二进制负载用 Uint8Array。

## 7. 安全模型

### 7.1 Electron 安全基线

| 配置项                        | 值      | 说明                          |
| ----------------------------- | ------- | ----------------------------- |
| `contextIsolation`            | `true`  | 渲染进程无法直接访问 Node API |
| `nodeIntegration`             | `false` | 渲染进程无 Node 权限          |
| `sandbox`                     | `true`  | 沙箱隔离                      |
| `webSecurity`                 | `true`  | 同源策略                      |
| `webviewTag`                  | `false` | 禁止 webview                  |
| `allowRunningInsecureContent` | `false` | 禁止混合内容                  |

### 7.2 CSP 策略

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';  (Lit 需要)
  img-src 'self' data:;
  connect-src 'self';
  font-src 'self';
```

### 7.3 IPC 安全

- 所有 IPC 通道通过 `contextBridge.exposeInMainWorld` 白名单暴露
- Preload 中不暴露 `ipcRenderer` 原始对象
- Main 进程中 `ipcMain.handle` 入口用 zod schema 校验参数
- 文件路径操作使用 `shell.openPath` 的安全包装
